## 1. UAE visa should only ever have Dubai/Sharjah — why does the manager dropdown show 8 emirates?

**Finished & tested? No — this is a real gap, not a false alarm.**

- The public-facing popup (`routes/web.php:387-392`, `partials/emirate_selector_modal.blade.php`) only shows emirates that have at least one **active** UAE visa package — right now that's just Dubai and Sharjah, which is why the customer-facing site currently shows 2 tabs.
- But the **manager's** "Create a Visa Package" dropdown (`ManagerVisaPricingController.php:34`, `manager/visa-pricing/index.blade.php:474-478`) pulls *all* active rows from `tbl_emirates` — all 8 seeded emirates (Abu Dhabi, Ajman, Dubai, Fujairah, Ras Al Khaimah, Sharjah, Umm Al Quwain, Western Region).
- There is nothing stopping a manager from creating a package for, say, Ajman — the moment that happens, a 3rd tab silently appears on the live site. This directly contradicts the scope Amer set in the Aug 25 call (3:48–4:27, action item: *"Update visa popup: logo > Dubai/Sharjah"*) — the product was scoped to two emirates only, but the tool that creates visa offerings was never restricted to match.

**Fix needed:** restrict the manager's emirate dropdown (or add a confirmation) to the emirates the business actually intends to sell, or explicitly acknowledge that "any emirate can be enabled" is intended admin behavior — this needs an explicit decision, not just a code fix.

## 2. Sharjah package: "processing fee" shows up multiple times — which one is real?

**Finished & tested? No — the client's confusion is legitimate; the UI is genuinely ambiguous even though the underlying data model is not broken.**

- There are really only **two** underlying DB fields: `uae_visa_packages.deposit_admin_fee` (a package-level default) and `uae_visa_package_deposits.deposit_admin_fee` (a per-nationality override).
- But the UI surfaces the *same* package-level column in two different-looking inputs with two different labels: "Default Processing Fee (AED)" in the edit view (`index.blade.php:248-249`) and "Processing Fee — per applicant (AED)" in the create modal (`index.blade.php:522-525`) — both write to the exact same column via `packageAttributes()`. Then the per-nationality table adds a third, visually similar "FEE" column that's a genuinely different field.
- Resolution order when charging a customer: nationality-specific row → package's own null-nationality row → package's legacy default → (Sharjah only) a company-wide fallback setting. This logic is sound; the labeling is not. A manager cannot tell from the UI alone that two of the three "fee" boxes they see are literally the same value.

**Fix needed:** UI/copy fix — one consistent label per distinct field, and a visible indicator when a per-nationality override exists.

## 6 & 8. New partner registration ("Sai") doesn't appear in Manager → Agents

**Finished & tested? No — this is the most serious bug found. The feature does not work at all.**

Confirmed behaviorally from the client's own screenshots: form submits successfully ("🎉 Partner registration successful! Welcome aboard!"), but the new partner never shows up under Manager Portal → Agents.

Per the code available to us (see caveat above — could not be double-checked against the exact live PHP):
- The modal's submit handler (confirmed live) posts to plain `/register` → `UserController::register()`.
- That handler creates a bare `users` row with only name/phone/email/password — it never sets `role` or `company_id`.
- `ManagerAgentsController::index()` only ever queries `users` **where** `role = 'company_agent'` **and** `company_id = <manager's company>` — so a row created this way can structurally never appear there, before or after any "approval."
- The only place this registration is even partially visible to staff is **Admin → Users** (a different login than the Manager Portal), via a fragile hack that encodes a pending/approved flag inside the `email_verified_at` column. Even clicking "Approve" there does not set `role`/`company_id`, so it's a dead end regardless.
- A correctly-built, working pipeline for this already exists: `/agent/register` → `AgentApplication` model → Manager reviews it at `/manager/agent-applications` → approval properly activates a real `company_agent` user that *does* show up in Manager → Agents. **The homepage "Create Partner Account" form was simply never connected to this existing, working system.**

This matches Amer's own words in the call (13:10): *"We were discussing on having something registered as automatic. Once they register, it should fall in here... I think this is still on pending."* — flagged over a week before the client's screenshots, and still broken.
